# The capability system

Track A. Consumes `docs/contract.md` and invents nothing outside it. Where this document
needed something the contract does not define, it is raised in section 9, "Contract change
requests", and is **not** used anywhere else in this document as though it existed.

Status: IMPLEMENTED. `CapabilityResolver` and `FeatureRegistry` in `Sources/Grux` are
this document, and `scripts/check-contract.py` fails the build when they drift apart.

Every claim about existing behaviour cites a file and a line under `Sources/Grux`, which
is published in this repository and can be read alongside the claim. Claims that are proposals are marked
**Proposed**. Claims I could not settle are marked **Uncertain**.

---

## 0. What this document is for, in one paragraph

Grux today has 476 Swift files, a 67-field config struct, 36 sidebar tabs, and no shared
answer to the question "can this feature actually run right now". Each surface answers it
privately, and most answer it badly: some throw, some render an empty view, some render a
control that writes a value nothing reads. The capability system replaces every private
answer with one mechanism: a feature **declares** what it needs, the app **resolves** what
is present, and a single gate **renders** the four states in the contract's section 3
table. The load-bearing requirement is not the happy path. It is that a control which is
not wired to anything must fail the build rather than ship.

---

## 1. Declaration

### 1.1 Why declaration is data and not code

A feature that declares its needs inside its own `View` body cannot be enumerated without
running the app. The registry has to be readable by a build step, because section 5 of this
document turns it into a build failure. So the declaration lives in a file the build reads.

The tree already has the right precedent. `SidebarIA.groups` at
`Sources/Grux/DesignSystem/SidebarModel.swift:27-74` is a static table of 36 tabs across 5
groups, and `LaunchRootView.swift:54-91` switches on it. The information architecture is
already data. What is missing is that a `SidebarItem`
(`SidebarModel.swift:13-18`) carries only `key`, `label` and `icon`. It says nothing about
what the tab needs.

### 1.2 The three closed sets, and why they are generated

Three vocabularies must be closed, meaning a name outside the set is a **compile error**,
not a runtime lookup miss:

| Set | Source of truth | Generated Swift type |
|---|---|---|
| Capabilities | contract sections 1.1, 1.2, 1.3 | `enum Capability` |
| Config keys | contract section 2.5 | `enum ConfigKey` |
| Features | see section 9, request CR-1 | `enum FeatureID` |

The human source of truth stays `docs/contract.md`. Beside it sits a machine-readable
mirror, `contract/capabilities.json` and `contract/config-keys.json`, and
`scripts/check-contract` fails when the mirror and the markdown tables disagree. The mirror
exists only because a build step cannot parse prose reliably. The markdown wins on conflict.

**Proposed.** A SwiftPM build tool plugin, `GruxContractGen`, reads the mirror and emits
`GeneratedContract.swift` into the plugin work directory. The package is
`swift-tools-version:5.9` (`Package.swift:1`) and builds with `swift build -c release
--arch arm64` (`build.sh:26`), so build tool plugins are available and run on every build,
including this one.

The generated file contains, for each capability, a case and its contract metadata:

```swift
// GENERATED by GruxContractGen from contract/capabilities.json. Do not edit.
enum Capability: String, CaseIterable, Hashable {
    case keyAnthropic          = "key.anthropic"
    case permScreenRecording   = "perm.screen_recording"
    case endpointRegistry      = "endpoint.registry"
    // ... one case per contract row, no others

    var label: String { ... }
    var remediation: String { ... }   // verbatim from the contract, never written at a call site
    var klass: CapabilityClass { ... }
    var isSecret: Bool { ... }
    // Deliberately NO isOptional. Optionality is a property of the feature-to-capability
    // edge, not of the capability, so a flag here would be reachable from every call site
    // while the state computation ignores it. That is the shape of a bug, not a
    // convenience. See contract 1.4, CR-5 amendment.
}
```

This is the whole point of generation. `Capability(rawValue:)` is never called at a feature
site, so a typo in a capability id cannot reach runtime. There is no `Capability(custom:)`
initialiser and no extension point. The set is closed by construction, which is what the
contract's opening paragraph demands and what a convention could not deliver.

### 1.3 The feature manifest

**Proposed.** One manifest per feature, at `Features/<id>.feature.json`, is the only way to
add a feature. Hand-written Swift cannot add one, because `FeatureRegistry` is generated and
has no public mutating surface.

```jsonc
{
  "id": "portfolio",
  "label": "Portfolio",
  "sidebar": { "group": "command", "icon": "square.stack.3d.up.fill" },

  "requires":  ["endpoint.registry"],
  "optional":  [],

  "reads":  ["grux.portfolio.registry_url", "grux.portfolio.projects"],
  "writes": [],

  "spends": false,
  "platform": { "minMacOS": "14.0" }
}
```

Field meanings, all of which are load-bearing later:

- `requires` and `optional` are `Capability` ids. The generator rejects any id not in the
  closed set. **The `optional` array IS the optionality**, and it belongs to the edge
  between this feature and that capability, not to the capability. Contract 1.4 no longer
  carries an `optional` flag: it was removed in the CR-5 amendment, because a two-set
  manifest leaves no "declared but unspecified" state for a global default to fill, so a
  default could never apply and would only be a second source of truth. The same capability
  is therefore free to sit in `requires` for one feature and `optional` for another, which
  is exactly what `endpoint.ollama` needs: `compare` cannot run without a local model
  server, `chat` merely loses a menu entry.
- `steps` and `optionalSteps` work identically for setup steps, and for the same reason.
  `step.agent_cli_installed` blocks `agents`, whose whole purpose is that tool, and merely
  degrades `chat`, which loses 4 of roughly 50 tools and must not render its default
  landing surface dimmed over that.
- `optional` is NOT the only producer of `degraded`. A tripped cost ceiling produces it too,
  per the state computation below and contract section 3. The earlier wording here claimed
  otherwise and was wrong on that axis independently of CR-5.
- `reads` and `writes` are `ConfigKey` ids. They are how section 5 knows which keys a
  feature is allowed to touch, and they are checked against what the code actually does, not
  trusted.
- `spends` marks a feature subject to the cost ceiling transition in contract section 3.
  A feature with `spends: false` may not call a paid provider, and the verifier in section
  5.6 enforces that by call site.
- `platform` is the only producer of `unavailable`. Absence of a key never produces it,
  which is the contract's rule that `unavailable` is impossibility and not absence.

The generator emits:

```swift
struct FeatureDescriptor {
    let id: FeatureID
    let label: String
    let requires: Set<Capability>
    let optional: Set<Capability>
    let steps:         Set<SetupStep>   // blocking, absence produces needsSetup
    let optionalSteps: Set<SetupStep>   // degrading, absence produces degraded
    let reads:  Set<ConfigKey>
    let writes: Set<ConfigKey>
    let spends: Bool
    let minMacOS: OperatingSystemVersion
}

enum FeatureRegistry {
    static let all: [FeatureID: FeatureDescriptor]   // complete, closed, build-time
}
```

`FeatureRegistry.all` is the enumerable object every later section depends on. The sidebar
is built from it. The verifier walks it. The settings screen is generated from it.

### 1.4 What declaration deliberately does not include

No remediation text. No error strings. No "what to show when it is missing". All of that
comes from `Capability.remediation`, which is contract text. A feature that could write its
own remediation string would immediately start writing worse ones, which is the reasoning
the contract already gives at section 1.

## 2. Resolution

### 2.1 Shape

**Proposed.** One `@MainActor final class CapabilityResolver: ObservableObject` with a
single published value:

```swift
@Published private(set) var states: [Capability: CapabilityState]

enum CapabilityState: Equatable {
    case present
    case absent(since: Date)
    case unknown          // probe in flight or never run; treated as absent for gating
}
```

Features never probe. A feature asks `resolver.state(of: .permScreenRecording)` and gets a
cached answer. Probing is centralised because the alternative is what exists today: 24
separate reads of `ProcessInfo.processInfo.environment` in `Sources/Grux`
(verified: `grep -rn 'ProcessInfo.processInfo.environment' Sources/Grux/ | wc -l` returns
24; the count across all of `Sources/` including `GruxShellCore` and `GruxAgentCore` is 39),
plus `ScreenCapturer.shared.hasPermission()` called independently at
`FocusWatcher.swift:113`, `GruxApp.swift:487`, `GruxApp.swift:774`, `GruxApp.swift:1046`,
`VisionTool.swift:30` and `ChatService.swift:1290`. Six call sites, six chances to disagree.

### 2.2 One probe per class, and only one

**Class `key`.** Resolved from Keychain only, per contract 2.4. `KeychainStore` already has
the right shape: `kSecClassGenericPassword` with service `com.dcj.grux`
(`KeychainStore.swift:80`, and documented at `KeychainStore.swift:14`; note the contract
cites line 14, which is the comment, the code is at 80, 125, 148 and 164). A key is
`present` when `SecItemCopyMatching` returns a non-empty value. The probe never returns the
value, only presence, so the resolver can be logged without leaking.

The contract's narrow environment exception (2.4, final paragraph) means the key probe also
consults the environment for `GRUX_ANTHROPIC_API_KEY` and its siblings, and fires the
one-time warning. It never consults the config file.

**Class `perm`.** Asked of the operating system, never cached across a probe, never guessed.
The probes are all cheap and synchronous:

| Capability | Probe |
|---|---|
| `perm.screen_recording` | `CGPreflightScreenCaptureAccess()` (already used at `ScreenCapture.swift:37`) |
| `perm.accessibility` | `AXIsProcessTrusted()` |
| `perm.microphone` | `AVCaptureDevice.authorizationStatus(for: .audio)` |
| `perm.calendar` | `EKEventStore.authorizationStatus(for: .event)` |
| `perm.contacts` | `CNContactStore.authorizationStatus(for: .contacts)` |
| `perm.notifications` | `UNUserNotificationCenter.getNotificationSettings` (async, the one exception) |
| `perm.automation` | `AEDeterminePermissionToAutomateTarget` with `askUserIfNeeded: false` |
| `perm.system_audio` | same preflight as screen recording, per the contract's own remediation text |

**Class `endpoint`.** A reachability probe, and this is the only class that can be slow, so
it is the only one with a policy:

- Never on the main thread, never on a view's `onAppear` synchronous path.
- Timeout 3 seconds. `EmpireSnapshotService` currently uses 12
  (`Empire/EmpireDashboard.swift:209`), which is fine for a user-triggered refresh and far
  too long for a gate that decides whether to draw a tab.
- Result cached for 60 seconds, and the cache is what the resolver publishes.
- Failure is `absent`, never an error. This is the contract's "a missing capability never
  surfaces as an error" applied at the probe rather than at the surface, so a feature cannot
  get an error to display even if it wanted one.
- An endpoint whose config key is empty is `absent` without any network call. No probe fires
  against an unconfigured host, which also means a fresh install makes zero outbound
  requests before the user configures something.

### 2.3 Observation: what wakes the resolver

Five triggers, and nothing else. Anything that is not on this list does not cause a re-probe,
which is deliberate: an unbounded set of triggers is how a resolver becomes a busy loop.

1. **Launch.** All classes probed once, concurrently, before the first frame. Endpoint
   probes do not block the first frame; they resolve into `unknown` and settle within the
   timeout.
2. **App activation.** `NSApplication.didBecomeActiveNotification`. This is the trigger that
   catches "the user granted a permission in System Settings while Grux was running", which
   is the single most common transition and the one most apps get wrong. macOS does not
   notify on a privacy change, so returning to the app is the honest moment to re-ask. All
   `perm` probes re-run; key and endpoint probes do not.
3. **Config commit.** The config store publishes a change set. Only capabilities whose
   backing key is in the change set re-probe. Committing an unrelated key does not re-probe
   the network.
4. **Keychain write.** `KeychainStore.set` posts an internal notification naming the key.
   Only that key's capability re-probes. There is no Keychain change notification from the
   system, so this is the only way a key transition is observed promptly, and it is
   sufficient because Settings is the only writer.
5. **Manual refresh.** A user-visible control on the setup card. Present because endpoint
   probes are cached for 60 seconds and a user who just started Ollama should not wait.

**Uncertain.** Whether a revoked permission is observable without app activation. macOS
terminates or degrades some capture paths on revocation rather than signalling, and
`CGPreflightScreenCaptureAccess()` is documented as reflecting the current grant but is not
documented as cheap enough to poll. The spec does not poll. If a permission is revoked while
Grux is frontmost and never leaves the foreground, the transition is caught by 2.4 below,
at the moment of use, and not before.

### 2.4 Mid-flight disappearance

This is the case that decides whether the system is real. A user revokes Screen Recording
while the focus loop is between a capture and a transmit; a token is deleted mid-upload; a
LAN host goes away between two pages of a paginated fetch.

**Proposed.** An operation that needs a capability holds a **lease**.

```swift
// Acquiring fails immediately and cheaply when the capability is absent.
guard let lease = await resolver.lease(.permScreenRecording, for: .focusLoop) else {
    return .notReady   // caller renders needs-setup; it does not throw
}
defer { lease.release() }
```

Three rules govern a lease, and they are the whole of the mid-flight contract:

**R1. Revocation cancels, it does not throw.** When a probe flips a capability to `absent`,
the resolver cancels every outstanding lease on it. Cancellation surfaces as Swift
structured-concurrency cancellation, so an operation that already honours `Task.isCancelled`
and `try Task.checkCancellation()` needs no new code path. A `CancellationError` reaching a
feature surface is rendered as `needs-setup`, never as an alert. This is why the mechanism is
cancellation and not a thrown domain error: the app already knows how to unwind cancellation,
and it does not know how to render 40 different domain errors consistently.

**R2. Partial work is preserved, never half-committed.** An operation that has produced
usable partial output writes it under the same all-or-nothing rule the rest of the tree
uses, `Data.write(to:options: .atomic)`, as at `Empire/EmpireDashboard.swift:153`. An
operation that cannot produce a coherent partial result discards and leaves the previous
state intact. What it must never do is leave a store half-updated, because the next launch
reads that store and has no way to know it is torn.

**R3. Nothing is retried automatically on revocation.** A revoked capability is a user
decision. Retrying is the app arguing with the user. The feature moves to `needs-setup`,
shows the contract remediation, and waits. The only automatic retry in the system is the
60-second endpoint cache expiry, which is a reachability question and not a consent question.

There is a fourth rule that only applies to capture and is stated in section 6.5, because it
is a stronger guarantee than R1: for capture, the check is re-run inside the capture call
itself, so a revocation between the gate and the shutter cannot produce a frame.

## 3. Rendering

The contract's section 3 table is the source of truth for **what** is shown. This section
specifies the **mechanism** that makes it impossible to show anything else.

### 3.1 The gate is the only way a surface is mounted

**Proposed.** `LaunchRootView.swift:54-91` currently mounts each tab's view directly, for
example `case .projects: ProjectsView()`. Every one of those 36 cases becomes:

```swift
case .portfolio: FeatureGate(.portfolio) { PortfolioView() }
```

`FeatureGate` owns all four renderings from the contract table. It resolves the feature's
state, and it invokes the closure **only** in `ready` and `degraded`. In `needs-setup` and
`unavailable`, `PortfolioView` is never constructed, so its `body` never runs, so it cannot
draw its own empty state, its own error banner, or its own "connect your account" card.
Those are the exact three things that today's surfaces do individually and inconsistently.

The mechanism that stops a developer bypassing the gate: `PortfolioView` and every other
registered surface conforms to `FeatureSurface`, whose only initialiser is
`internal init(gate: FeatureGateToken)`. `FeatureGateToken` has a `private init` and is
constructible only inside `FeatureGate`. Writing `PortfolioView()` at any other site does
not compile. This is worth the small ceremony because bypassing the gate is otherwise a
one-word mistake that nothing catches.

### 3.2 State computation

```
state(of feature) =
    if !platformSatisfied(feature)                       -> .unavailable(reason)
    else if !requires.allSatisfy(present)
         || !steps.allSatisfy(satisfied)                 -> .needsSetup(missing:
                                                              requires.filter(absent)
                                                            + steps.filter(unsatisfied))
    else if spends && costCeilingReached                 -> .degraded(note: ceilingNote)
    else if !optional.allSatisfy(present)
         || !optionalSteps.allSatisfy(satisfied)         -> .degraded(missing:
                                                              optional.filter(absent)
                                                            + optionalSteps.filter(unsatisfied))
    else                                                 -> .ready
```

**Steps are evaluated here, alongside capabilities, and that is a correction.** An earlier
version of this function read `requires` and `optional` only. `SetupStep` appeared nowhere
in this document and `FeatureDescriptor` carried no step fields, so the contract could
declare `step.first_frame_reviewed` as gating the focus loop and this mechanism would
compute `.ready` anyway, with both permissions and a model key present and the first
capture frame still unreviewed. The capture privacy gate, which contract 5.4 calls the
thing that gates the whole loop, would have opened silently.

The failure is worth naming precisely because it repeats the defect this document helped
diagnose. The argument that removed `optional: Bool` from the capability descriptor was
that the state computation never consulted it, so it was decorative. Adding `steps` to the
contract's Feature shape and to the registry tables without adding them here reproduced
that exact shape one layer down: a field declared everywhere and read nowhere. Contract
3.1 requires steps to render in the same card with no special case, so a per-feature
hardcode for focus is not an acceptable substitute.

`needsSetup` lists capabilities before steps, per contract 3.1, because capabilities
usually gate the steps.

Order matters and is fixed here so no surface reorders it. `unavailable` outranks everything
because a machine that cannot run the feature should not be asked for a key. The cost ceiling
sits between required and optional because contract section 3 says the ceiling produces
`degraded`, and a feature that is already `needs-setup` for a missing key should show the key,
not the ceiling.

`CapabilityState.unknown` counts as absent for gating. A tab whose endpoint probe has not
settled shows `needs-setup` for at most the probe timeout, then settles. It never shows a
spinner in place of the state, because a spinner is a fifth state and the contract has four.

### 3.3 Sidebar

`SidebarItem` (`SidebarModel.swift:13-18`) gains one field, `feature: FeatureID?`, and the
badge is computed, never assigned:

| State | Row rendering |
|---|---|
| `ready` | Label and icon at full opacity. No badge. |
| `needs-setup` | Label and icon at full opacity, plus a 5pt dot badge trailing the label. The dot is the same shape already used for the primary-brand marker at `Empire/EmpireDashboard.swift:396`, so it is not a new visual idiom. |
| `degraded` | Label and icon at full opacity. No badge. Identical to `ready` in the sidebar, because contract section 3 gives `degraded` no sidebar treatment and the note lives on the surface. |
| `unavailable` | Row omitted from `SidebarIA.groups` at render time. Reappears with a struck-through label when Settings, Show unavailable features is on. |

The mechanism that keeps this honest: the sidebar builds its rows by mapping over
`FeatureRegistry.all`, so a row cannot exist for a feature that is not registered, and a
registered feature cannot be given a hand-written badge. The dot is a function of
`state(of:)` and there is no setter.

A row in `needs-setup` stays **clickable**. Hiding or disabling it is the failure mode that
makes a product feel broken instead of unfinished: the user cannot discover what the feature
is or what it wants. Clicking it opens the surface in its `needs-setup` rendering, which is
where the remediation lives.

### 3.4 Surface renderings

**`ready`.** The feature's own view, unmodified. The gate adds nothing.

**`needs-setup`.** The gate renders the feature's view **only if the feature provides a
static preview**, and otherwise renders a neutral placeholder. Contract section 3 asks for
"the feature's own UI, dimmed and non-interactive". The mechanism is
`.disabled(true)` plus `.opacity(0.4)` plus `.allowsHitTesting(false)` on the previewed
content, with the setup card as an overlay. The important constraint is that the previewed
content is a **static preview**, a `FeatureSurface.preview` that takes no live data and
performs no I/O. Dimming the live view would mean constructing it, which would mean it runs
its own fetch, which is exactly the leak this gate exists to prevent. A feature that does not
supply a preview gets a neutral placeholder, and that is an acceptable outcome, not a defect.

The setup card lists one row per missing required capability, each row being
`capability.label`, `capability.remediation`, and a button. The button's destination is
derived, not hand-written: `Capability.klass` decides it. `key` and `endpoint` open the
Settings pane owning the capability's config key, which the generator knows from the key's
`owner` column in contract 2.5. `perm` opens the System Settings pane via the documented
`x-apple.systempreferences:` URL for that privacy category. There is no free-text
destination, so a button cannot point somewhere wrong.

**`degraded`.** The feature's own live view, fully interactive, plus exactly one inline note
carrying `capability.remediation` verbatim, or the ceiling note from contract section 3 when
the cause is cost. The note is dismissible, and dismissal is remembered per capability per
launch, not forever: the contract says `degraded` is never silent, and a permanently
dismissed note is silent. One note, never two. When two optional capabilities are missing,
the note lists both in one control.

**`unavailable`.** One sentence, from the platform reason. No setup card, no button, no
retry. The gate does not construct the feature's view at all.

### 3.5 The rendering rule that has no exception

`FeatureGate` has no escape hatch parameter. There is no `FeatureGate(.portfolio,
allowRawRender: true)`. If a surface genuinely cannot be expressed through the gate, that is
a change to the gate, reviewed once, rather than a flag that spreads.

## 4. The degradation contract

What a feature may do when a capability is missing, stated as an allow list and then a never
list. The never list is the operative half.

### 4.1 Allowed

- Render its `needs-setup` or `degraded` state through the gate.
- Read and display data it already has on disk from a previous successful run, clearly marked
  as cached. `EmpireSnapshotStore` already does this correctly:
  `Empire/EmpireDashboard.swift:138` sets `servingStale` and the header renders a `CACHED`
  chip at `Empire/EmpireDashboard.swift:270-277`. That pattern is the model.
- Offer the manual refresh from 2.3, trigger 5.
- Fall back to a genuinely equivalent local path and report `degraded`. The contract's own
  worked example is the spoken nudge falling back to `AVSpeechSynthesizer` at
  `SpeechEngine.swift:91` when `key.elevenlabs` is absent.

### 4.2 Never

1. **Never throw to the surface.** No alert, no `fatalError`, no red banner, no
   `error.localizedDescription` in the UI. `EmpireOpsSection` violates this today: it renders
   the raw `error.localizedDescription` in an orange banner at
   `Empire/EmpireDashboard.swift:451-462`, fed from `Empire/EmpireDashboard.swift:137`. A
   stranger with no registry configured sees a networking error, which the contract forbids.
2. **Never render an empty state that hides a fixable cause.** "No snapshot yet" at
   `Empire/EmpireDashboard.swift:440-449` is the failure this rule names. It is truthful and
   useless: nothing tells the user there is a URL to set.
3. **Never fall back to a value the user did not supply.** No default host, no default
   registry, no bundled endpoint. Contract section 1.3 states this and gives the reason. The
   three hardcoded base URLs at `Empire/EmpireDashboard.swift:193-197` are the violation, and
   section 7 migrates them.
4. **Never fall back to a cheaper paid provider silently.** A provider substitution that
   costs money is a `degraded` transition with a note, or it does not happen.
5. **Never spend after the ceiling.** A feature with `spends: true` acquires a spend lease
   from the cost meter, and the lease is refused past `grux.cost.daily_ceiling_usd`. Refusal
   produces `degraded` with the contract's ceiling note. The current mechanism is a
   call-count ceiling, not a dollar ceiling: `FocusWatcher.swift:196` compares
   `cloudCallsToday >= tier.maxCloudCallsPerDay` and, when it trips, logs to `NSLog`
   (`FocusWatcher.swift:197`) and silently sets `shouldCallCloud = false`. Console-only, and
   invisible to the user. That is the exact "silent pause" the contract rules out.
6. **Never capture, record, or transmit anything while a required capability is absent.**
   Section 6 makes this structural for capture rather than relying on this sentence.
7. **Never write user config to work around a missing capability.** A feature may not set
   `grux.focus.enabled = false` because a permission is missing. The user's intent and the
   machine's state are different facts and must not be merged, or the permission grant will
   not restore the feature.
8. **Never poll a failing endpoint faster than the 60-second cache.** A `needs-setup`
   surface that is open must not become a network loop.
9. **Never log a secret, present or absent.** The resolver publishes presence, not values,
   which makes the whole `states` map safe to log and to show in a diagnostics view.

## 5. Killing the dead-toggle class by construction

This is the section that has to earn the rest. A convention will not do it, because the three
bugs below were all written by people who knew the convention.

### 5.1 The three verified defects

Verified by grep in the private tree on the `main` worktree
(`git rev-parse --abbrev-ref HEAD` returns `main` in the build worktree).

**Defect A, `judgeText`: dead code.** `grep -rn 'judgeText' Sources/ Tests/` returns
**exactly one line**, `Sources/Grux/FocusWatcher.swift:524`, which is its own declaration:
`private func judgeText(snapshot:activeApp:state:currentTask:) async throws -> Verdict`. It
is `private`, so in Swift it is reachable only from within `FocusWatcher.swift`, and it is
referenced nowhere in that file. It is provably unreachable.

This matters more than "some dead code". `judgeText` is the OCR path, and it contains the
OCR fencing the contract cites at section 5.1: `SecretRedactor.wrapAsUntrusted("screen_ocr",
...)` at `FocusWatcher.swift:530`. **The OCR fence is inside the dead function.** The
contract's statement that "the OCR is fenced" is true of the code as written and false of the
code as executed, because that code never executes. This is reported in section 10.

**Defect B, `focusUseVision`: a toggle nothing acts on.** `grep -rn 'focusUseVision' Sources/
Tests/` returns **exactly six lines**, and not one of them is a behavioural read:

| Line | Kind |
|---|---|
| `Models.swift:594` | stored property declaration |
| `Models.swift:645` | `CodingKeys` case |
| `Models.swift:691` | `init` parameter, defaulted to `true` |
| `Models.swift:743` | `init` assignment |
| `Models.swift:799` | `decodeIfPresent`, defaulted to `true` |
| `LaunchRootView.swift:863` | `let modelLabel = cfg.focusUseVision ? "vision" : "OCR"` |

The single non-declaration use is a **label**. The focus banner tells the user which analysis
mode is active, and the value it reports controls nothing. `FocusWatcher.tick` always takes
the vision path: it captures at `FocusWatcher.swift:169`, encodes JPEG at
`FocusWatcher.swift:213`, and calls `judgeVision` at `FocusWatcher.swift:221`, with no branch
on `focusUseVision` anywhere. Setting it to `false` in `config.json` changes the banner text
and nothing else. Defects A and B are the same bug seen from two ends: B is the switch, A is
the wire it was supposed to throw.

**Defect C, the capture-interval slider: a control bound to the wrong quantity.** The Settings
slider loads from and stores to `captureIntervalSeconds`
(`SettingsView.swift:1263` and `SettingsView.swift:1311`), and the focus banner reports it as
the cadence: `let intervalLabel = "every \(max(10, cfg.captureIntervalSeconds))s"` at
`LaunchRootView.swift:860`. The focus loop does not read it. `FocusWatcher.swift:110` computes
`let interval = TimeInterval(max(1, tier.cadenceSeconds))` and that value is what
`scheduleNext(after:)` receives at `FocusWatcher.swift:149`, `:209` and elsewhere.
`captureIntervalSeconds` is read for real in only one behavioural place, and it is not the
loop: `ChatService.swift:1351` uses it to estimate elapsed minutes per tick
(`let tickMin = max(1, AppState.shared.config.captureIntervalSeconds / 60)`).

So the slider moves, the banner agrees with the slider, and the loop ignores both. This is
the worst of the three, because it is not merely inert: it is confidently wrong, and it is
wrong in the one place a user goes to control how often they are photographed.

### 5.2 What the mechanism must make impossible

Three distinct impossibilities, because these are three distinct bugs:

- **I1.** A config key that no code acts on cannot exist.
- **I2.** A runtime quantity cannot have two competing sources.
- **I3.** A `private` function with no reference in its own file cannot survive a build.

### 5.3 I1, enforced by splitting reads into `effective` and `display`

**Proposed.** `GruxConfig` (`Models.swift:563`, roughly 67 stored properties) stops being read
by property access. There are exactly two generated accessors, and they are the only way to
read a config key:

```swift
extension ConfigStore {
    /// Read a value that WILL change what the program does.
    func effective<T>(_ key: ConfigKey.Typed<T>) -> T

    /// Read a value ONLY to show it to a human. Cannot influence control flow.
    func display<T>(_ key: ConfigKey.Typed<T>) -> Displayed<T>
}
```

`Displayed<T>` wraps the value and exposes only `description` and formatting. It is not
`Equatable` against `T`, has no `==`, and does not conform to `Bool`, so
`if config.display(.focusCadenceSeconds) { ... }` does not compile, and neither does a
ternary on a displayed value. A display read cannot become a branch, which is what makes the
distinction mechanically meaningful rather than a naming convention.

`ConfigKey` is generated from contract 2.5 and has one case per row, so **`ConfigStore` can
only address keys the contract defines.** There is no `ConfigStore[dynamicMember:]`, no
string-keyed subscript, and no case for anything outside the table. This is the first and
strongest arm, and it is the one that kills Defect B.

The verifier, `scripts/check-contract`, then adds two rules over the generated accessor call
sites, as a backstop for keys that legitimately enter the namespace later:

- **K1, orphan key.** Every non-secret key in the contract 2.5 namespace must have at least
  one `effective(...)` site. Zero fails the build.
- **K2, lying display.** A key with at least one `display(...)` site and zero `effective(...)`
  sites fails the build, because it is strictly worse than an unused key. It makes a claim to
  the user about behaviour that nothing implements.

#### How Defect B is caught

Two arms, in order, and the first one is sufficient.

**Arm 1, the closed namespace, is what actually kills it.** `focusUseVision` is a stored
property on `GruxConfig` at `Models.swift:594`. It has **no key in contract 2.5**: the
`focus` domain owns exactly three keys there, `grux.focus.enabled`,
`grux.focus.cadence_seconds` and `grux.focus.nudge_after_strikes`, and none of them is a
vision toggle. Once config is addressed only through the generated `ConfigKey`, there is no
case for it, so the field cannot exist and `cfg.focusUseVision` at `LaunchRootView.swift:863`
does not compile:

```
error: value of type 'ConfigStore' has no member 'focusUseVision'
  Sources/Grux/LaunchRootView.swift:863
  Config keys are generated from docs/contract.md section 2.5.
  To add one, change the contract first.
```

That error message is the mechanism working as designed. The developer's only routes forward
are to delete the label, or to change the contract deliberately and in public. Neither route
is "leave the toggle in and move on", which is how it survives today.

**Arm 2, K2, is the backstop if the contract gains the key.** Suppose someone argues the OSS
build should support an OCR-only mode and adds a vision-mode key to contract 2.5. The moment
they do, the key has one `display(...)` site at `LaunchRootView.swift:863` and zero
`effective(...)` sites, because `FocusWatcher.tick` branches on nothing: it captures at
`FocusWatcher.swift:169`, encodes at `:213` and calls `judgeVision` at `:221`
unconditionally. K2 fails the build and names both facts. So the bug is unreachable whether or
not the key exists, which is the property worth having, because "we will just never add that
key" is a discipline claim and this document does not accept those.

**Uncertain, and it is Track B's call, not this document's.** Whether an OCR-only mode should
exist at all. If the OSS build ships vision-only, the correct fix is to delete the field, the
label, and `judgeText`, and no key is ever proposed. This specification does not propose one,
and section 9 deliberately contains no request for it.

### 5.4 I2, enforced by phantom-typed effects

**Proposed.** A **runtime effect** is a quantity the program acts on: a loop interval, a
threshold, a ceiling. Effects are declared in the same mirror as the keys, and the generator
emits a phantom-typed wrapper per effect:

```swift
enum FocusCadence: EffectTag {}          // generated, uninhabited, purely a type tag

struct Effectful<Tag: EffectTag, Value> {
    let value: Value                      // internal, obtainable only via ConfigStore
}

extension ConfigStore {
    func effect(_ e: Effect.FocusCadence) -> Effectful<FocusCadence, TimeInterval>
}
```

`FocusWatcher.scheduleNext` changes signature to
`scheduleNext(after: Effectful<FocusCadence, TimeInterval>)`. The only producer of that type
is `ConfigStore.effect(_:)`. The generator emits exactly one producer per effect, because the
mirror allows exactly one source key per effect, and `check-contract` fails on a duplicate.

**Defect C is caught at compile time.** `FocusWatcher.swift:110` computes
`TimeInterval(max(1, tier.cadenceSeconds))`, a bare `TimeInterval`, and passes it to
`scheduleNext`. Under the new signature that is a type error:

```
error: cannot convert value of type 'TimeInterval' to expected argument type
       'Effectful<FocusCadence, TimeInterval>'
  Sources/Grux/FocusWatcher.swift:110
  The only source of FocusCadence is grux.focus.cadence_seconds.
```

The developer cannot proceed without deciding which source wins. The correct resolution is
already implied by the contract: `grux.focus.cadence_seconds` has default "tier default"
(contract 2.5), so `GruxTier.cadenceSeconds` (`Models.swift:340`) becomes the **default
provider** for the key rather than a competing reader, and the slider becomes the override.
`SmokeTest.swift:544-556` already asserts the tier cadences are positive and monotone, and
those assertions keep working, because the tier table stays; only its role changes.

This is the arm that makes the class of bug unrepresentable rather than merely detected. A
type error cannot be shipped past a reviewer who is not paying attention.

### 5.5 I3, enforced by a provable-deadness check

Swift's `private` is scoped to the enclosing declaration and its extensions **within the same
file**. So for a `private func`, the set of possible call sites is exactly the set of
references in that one file. A `private func foo` whose identifier appears exactly once in
its file is therefore provably dead, with no whole-program analysis and no false positives
from other files.

**Proposed.** `scripts/check-contract` scans every file under `Sources/Grux` for
`private func <name>` and fails when `<name>` occurs exactly once in that file.

**Defect A is caught directly.** `judgeText` occurs once in `FocusWatcher.swift`, and once in
the entire tree. The build fails with:

```
error: private func judgeText is unreachable
  declared at Sources/Grux/FocusWatcher.swift:524
  references in file: 0
  It also contains the only OCR fence (line 530), which therefore never runs.
```

Two honest caveats. First, this check is narrower than "find all dead code": it says nothing
about `internal` or `public` functions, whose call sites can be anywhere. That narrowness is
what makes it sound. Second, it will find other pre-existing dead private functions across
476 files, and adopting it means either fixing or explicitly annotating them. The annotation
escape is `// swift-dead-ok: <reason>` on the declaration line, and the annotation itself is
greppable, countable, and reviewable, which a silent skip is not.

### 5.6 Where the checks run, and how strong that is

| Check | Mechanism | Strength |
|---|---|---|
| Unknown capability or config id | generated closed `enum` | Compile error. Unrepresentable. |
| Feature added without a manifest | `FeatureRegistry` generated, no mutating API | Unrepresentable. |
| Surface mounted outside the gate | `FeatureGateToken` has a `private init` | Compile error. Unrepresentable. |
| Display read used as a branch | `Displayed<T>` is not `Bool` and not `Equatable` to `T` | Compile error. Unrepresentable. |
| Two sources for one effect | phantom type `Effectful<Tag, Value>` | Compile error. Unrepresentable. |
| K1 orphan key | `check-contract`, run as a SwiftPM build command | Build failure. |
| K2 lying display | `check-contract` | Build failure. |
| I3 dead private func | `check-contract` | Build failure. |
| Feature reads a key not in its manifest | `check-contract` cross-checks call sites against `reads` | Build failure. |
| `spends: false` feature calling a paid provider | `check-contract` call-site scan | Build failure. |
| Secret key in a sample config or fixture | `check-contract`, contract 2.4 point 4 | Build failure. |

**Honest limitation.** SwiftPM build tool plugins run sandboxed and see only their declared
inputs. Declaring all 476 files under `Sources/Grux` as inputs to a build command is
supported but makes the check re-run on any source change, which is the correct behaviour and
also a real build-time cost. **Uncertain:** whether that cost is acceptable in practice at
this tree size. If it is not, the documented fallback is to run `check-contract` as a
`swift test` case plus a pre-commit hook. **The fallback is weaker and the spec says so
plainly**: it fails the test suite rather than `swift build`, so a developer running only
`./build.sh` would not see it. The compile-error arms in the top half of the table are
unaffected by this choice, which is the reason the strongest guarantees were put in the type
system rather than in the script.

## 6. The capture privacy layer

Contract sections 5.1 through 5.4 define the policy. This section specifies the mechanism.

**Verified gap.** `grep -rniE 'excludeApp|excludedBundle|blocklistApp|excludedApps' Sources/
Tests/` returns zero matches, exit status 1. Nothing in the tree excludes any app from
capture.

### 6.1 Where the check must sit, and why not in the focus loop

`FocusWatcher` is not the only capturer. Every current caller of `ScreenCapturer`:

| Site | Call | Purpose |
|---|---|---|
| `FocusWatcher.swift:169` | `captureOnly()` | the focus loop |
| `VisionTool.swift:48` | `cachedOrCapture(forceFresh:)` | the `read_screen` model tool |
| `Foundry/Signals/UXAuditSource.swift:173` | `ScreenCapturer.jpegData(...)` | Foundry UX audit |

A check placed in `FocusWatcher` is bypassed by the model tool, which is the more dangerous
path, because a model can ask for a screenshot at any moment with no cadence and no tier
prescreen. **The exclusion check therefore lives inside `ScreenCapturer`, above
`captureMainDisplay()` (`ScreenCapture.swift:119`), and every entry point routes through
it.** `captureAndOCR` (`:52`), `captureOnly` (`:64`) and `cachedOrCapture` (`:77`) all funnel
into the same private capture, so one gate covers all three.

The tree already contains a correct one-app version of exactly this gate, which is worth
citing as precedent rather than inventing a new idiom: `FocusWatcher.swift:130` refuses to
analyse Grux itself, comparing `activeApp.bundleId` to `Bundle.main.bundleIdentifier` and
returning before any capture. The shape is right. It is hardcoded to one bundle id, it lives
in the wrong layer, and it skips the analysis rather than the capture.

### 6.2 Why exclusion must precede capture rather than filter after

Contract 5.2 says "not captured then discarded: not captured". The mechanism reasons:

1. **A frame that exists can leak.** A `CGImage` held even briefly can reach a crash log, a
   memory dump, the snapshot cache at `ScreenCapture.swift:28`, or a future refactor that adds
   a debug write. `ScreenCapturer.saveScreenshot(_:label:)` at `ScreenCapture.swift:150`
   already writes frames to disk on demand. A post-filter is one careless call away from
   being bypassed.
2. **The cache makes discard unsound.** `captureOnly` unconditionally assigns
   `cachedSnapshot = snap` at `ScreenCapture.swift:68` before any caller can inspect it. A
   filter that runs in the caller has already lost: the frame is in the cache.
3. **A post-filter has to be correct at every call site. A pre-filter has to be correct
   once.** Three capture sites today, and the Foundry one was added later than the other two,
   which is the pattern that will continue.

### 6.3 Two levels of exclusion

Level 1 alone is insufficient, and this is the honest part most designs skip. `captureMainDisplay`
captures the **whole display**, not the frontmost window: `SCContentFilter(display: display,
excludingWindows: [])` at `ScreenCapture.swift:124`. A password manager sitting beside the
editor is photographed even when the editor is frontmost. Frontmost-app checking does not
solve this.

**Level 1, the frontmost gate.** Before any capture, resolve `ActiveApp.current()` and match
`bundleId` against `grux.capture.excluded_bundle_ids` and `windowTitle` against
`grux.capture.excluded_window_titles` (case-insensitive substring, per contract 5.2). On a
match, return `.excluded(reason:)` without calling `captureMainDisplay()`. No `CGImage` is
constructed. Nothing enters the cache.

**Level 2, compositor exclusion.** For every other on-screen window, exclude it at the
compositor so its pixels never enter the frame. `SCShareableContent` already returns the
window list at `ScreenCapture.swift:120`, and the filter's second parameter is already there
and already empty at `ScreenCapture.swift:124`. Verified against the ScreenCaptureKit
reference: `SCContentFilter.init(display: SCDisplay, excludingWindows: [SCWindow])`,
`SCWindow.title: String?`, `SCWindow.owningApplication: SCRunningApplication?`, and
`SCRunningApplication.bundleIdentifier: String`, all macOS 12.3 and later, against a package
minimum of macOS 14 (`Package.swift:6`).

```swift
let excluded = content.windows.filter { w in
    if let b = w.owningApplication?.bundleIdentifier, policy.excludesBundle(b) { return true }
    if let t = w.title, policy.excludesTitle(t) { return true }
    return false
}
let filter = SCContentFilter(display: display, excludingWindows: excluded)
```

The excluded window's pixels are never composited into the returned image. This is stronger
than any redaction, because there is nothing to redact.

**A material benefit of the level 2 source.** `SCWindow.title` arrives with Screen Recording
permission. The existing window-title path does not: `ActiveApp.frontWindowTitle`
(`ActiveApp.swift:20-31`) uses `AXUIElementCopyAttributeValue`, which requires
`perm.accessibility`, and on failure returns `nil`, which `ActiveApp.current()` converts to
`""` at `ActiveApp.swift:16`. **Title-based exclusion built on the Accessibility path fails
open, silently.** Without Accessibility granted, every window title is the empty string,
every title rule misses, and capture proceeds. The spec therefore requires that the
authoritative title source for exclusion is `SCWindow.title`, and that
`ActiveApp.windowTitle` is used only for display and for the level 1 fast path where a
non-empty title is available.

Because the level 2 window list is authoritative, level 1 also re-derives the frontmost
window's title from `SCShareableContent` rather than from the AX path, so the gate does not
depend on a permission the contract does not require for capture.

### 6.4 Cache correctness

The cache at `ScreenCapture.swift:77-86` self-invalidates on a frontmost-bundle change
(`ScreenCapture.swift:81`), which is good and not sufficient. Two additions:

1. `ScreenSnapshot` gains `exclusionsApplied: Set<String>`, the bundle ids excluded at capture
   time. `cachedOrCapture` returns the cached frame only when the current exclusion policy
   would produce the same set. A policy edit therefore invalidates the cache immediately,
   rather than serving a frame captured under the old policy for up to the 4-second TTL
   (`ScreenCapture.cacheTTL`, `ScreenCapture.swift:34`).
2. A policy change calls `invalidateCache()` (`ScreenCapture.swift:48`) directly.

### 6.5 Revocation between the gate and the shutter

Stronger than lease rule R1 in section 2.4, because capture is the one place where losing a
race produces a durable artifact. `CGPreflightScreenCaptureAccess()` is re-checked inside the
private capture, immediately before `SCScreenshotManager.captureImage`
(`ScreenCapture.swift:131`), and not only at the caller's guard
(`FocusWatcher.swift:113`, `VisionTool.swift:30`, `ChatService.swift:1290`). The cost is one
synchronous preflight per capture. That is a negligible price for closing a window in which a
revoked permission still yields a frame.

### 6.6 Seeding

Contract 5.2 requires the lists ship seeded. **Proposed** seeds, as data in the contract
mirror rather than in Swift, so they are reviewable without reading code:

- `grux.capture.excluded_bundle_ids`: password managers, banking and finance apps, Messages,
  Mail, FaceTime, and Keychain Access, per the contract's own enumeration. Grux's own bundle
  id joins the list, which replaces the hardcoded self-check at `FocusWatcher.swift:130` with
  a data row and removes a special case.
- `grux.capture.excluded_window_titles`: case-insensitive substrings covering private
  browsing window titles and common bank and password-manager window titles, per contract 5.2.

Seeds are defaults, not a floor. The user may remove a seeded entry, and the settings UI says
plainly what removing it means. A list the user cannot edit is a list the user does not trust.

### 6.7 The transmission indicator

Contract 5.3: the indicator fires on **actual transmission**, not on the loop running. The
mechanism is that the indicator is driven from the transmit boundary, and the transmit
boundary is a single function.

Today there are three places a captured frame leaves the machine, and they are separate code
paths: `FocusWatcher.swift:213` encodes JPEG and `FocusWatcher.swift:221` calls `judgeVision`
(declared at `:501`), whose network call is `claude.completeVision` at `FocusWatcher.swift:508`;
`VisionTool.swift:52` encodes and posts via `client.completeVision` at `VisionTool.swift:73`;
`UXAuditSource.swift:173` encodes for the Foundry audit.

**Proposed.** All three route through one `FrameTransmitter.send(_:to:)`. The indicator is a
`@Published` counter that `FrameTransmitter` increments on entry and decrements on
completion, so the indicator is on for exactly the duration of an in-flight frame upload and
cannot be on at any other time. There is no `indicator.show()` call anywhere, because a
manual call is a manual call that can be forgotten, and the whole point of contract 5.3 is
that the indicator must be trustworthy.

`grux.capture.indicator_enabled` defaults to `true` and, per contract 5.3, has no UI control
in v1. The mechanism for "cannot be set to false in v1" is that the generated key descriptor
carries no editable surface, so no control can bind to it and the Settings generator emits
nothing for it. Setting it to `false` by hand-editing the config file is ignored by the
reader, in the same shape as contract 2.4 point 2 ignores a plaintext secret.

The correctness argument for tying the indicator to transmission rather than to capture is
the contract's, and the code supports it: the local prescreen at `FocusWatcher.swift:179-188`
suppresses most frames, so on a prescreen-enabled tier the loop captures far more often than
it transmits. An always-on indicator would be on nearly all the time and would teach the user
to ignore it.

### 6.8 First-frame review

Contract 5.4: while `grux.capture.first_frame_reviewed` is `false`, the focus loop is
`needs-setup` regardless of every other capability.

Mechanism. The flag is checked in `FeatureGate`'s state computation for the focus feature,
which places it ahead of any capture, and it is also checked in the loop's own guard, which
currently sits at `FocusWatcher.swift:112-121`. Two checks, because the gate protects the UI
and the guard protects the loop, and the loop is started from `GruxApp.swift:774` without
going through the UI.

The review screen shows two things side by side, and the specification is exact about what
each one is:

- **The image**, exactly the JPEG that `ScreenCapturer.jpegData` would produce at the same
  parameters the focus loop uses: `maxDimension: 1280, quality: 0.55`
  (`ScreenCapture.swift:90`). Not a full-resolution preview, because the point is to show
  what is sent.
- **The text**, exactly the prompt body after `SecretRedactor.redact(body)` at
  `FocusWatcher.swift:498`. Not a summary and not a description.

Honest scope note: redaction runs on the **prompt body**, not on the image. The image is sent
unredacted, and the review screen must not imply otherwise. Stating that plainly on the review
screen is better product than quietly omitting it, and it is the accurate description of
`FocusWatcher.swift:498`, which redacts a `String`.

Nothing is transmitted before confirmation. Declining leaves the flag `false`, and the
feature stays `needs-setup`, which is a state the user can leave at any time and not a dead
end.

## 7. Migrating the hardcoded features

### 7.1 The general recipe

Six steps. Steps 1 through 4 are mechanical. Steps 5 and 6 are not, and the recipe says so.

1. **Find the hardcodes.** Grep the feature for hosts, IPs, ids, paths, and names. For this
   tree the productive patterns are `<private-host>` (39 hits across `Sources/`), a hardcoded
   RFC1918 address (14 hits), and any string literal that is a person's or a company's proper noun.
2. **Map each to a contract key.** Every hardcode becomes a key from contract 2.5 or it is
   deleted. It may not become a new key invented at the call site. If contract 2.5 has no
   home for it, the contract changes first, per its own opening paragraph.
3. **Declare the manifest.** Write `Features/<id>.feature.json` with `requires`, `optional`,
   `reads`, `writes`, `spends`, `platform`.
4. **Route the surface through the gate.** Replace the direct mount in
   `LaunchRootView.swift:54-91` with `FeatureGate(.<id>) { ... }`, and delete the feature's
   private empty state, its error banner, and its "not configured" copy. The gate owns all
   three now, and leaving them in means two things can render at once.
5. **Replace the fallback chain with a single configured value.** A three-host failover list
   is a private-network assumption wearing a resilience costume. One user-supplied endpoint,
   one probe, one honest `needs-setup`.
6. **Deal with the data schema.** This is the step that is not mechanical, because a schema
   built around one person's business encodes that person's business in its field names.

### 7.2 Worked example: the portfolio dashboard

The private tree calls it the Empire dashboard. It is the hardest of the 12 because it is
entangled in all three ways at once: a private host, a private LAN address, and a data file
of real brands.

#### What a stranger sees, state by state

**`unavailable`.** Not reachable for this feature. There is no macOS version below which a
portfolio table cannot render, and contract section 3 reserves `unavailable` for
impossibility. A fresh install must never show this row struck through.

**`needs-setup`,** which is what a stranger sees on first launch. The sidebar shows
**Portfolio** under Command with a small dot. Clicking it opens the surface: a static preview
of the table at 40% opacity and non-interactive, with a setup card over it reading

> **Project registry**
> Point Grux at your project registry URL in Settings, or add projects by hand.
> [ Open Settings ]

verbatim from contract 1.3. No error. No host name. No IP address. No mention of a Mini, a
tailnet, or port 3854. Zero network requests, because 2.2 forbids probing an unconfigured
endpoint. A stranger learns in one screen what the feature is and what it wants.

**`ready`.** The registry URL resolves, the probe succeeds, the table renders the user's own
projects. The KPI tiles at `Empire/EmpireDashboard.swift:302-316` render whatever the user's
registry supplies, and a column with no data shows `n/a`, which the existing `money(_:_:)`
helper already does at `Empire/EmpireDashboard.swift:424-429`.

**`degraded`.** Reachable only via the cost ceiling, and `spends` is `false` here, so in
practice this feature has no `degraded` state. The honest consequence is that a **reachable
registry serving stale data is `ready` with the existing `CACHED` chip, not `degraded`**.
That is correct under the contract: `degraded` means an optional capability is missing, and
staleness is not a missing capability.

#### What cannot be migrated mechanically

Six things, stated plainly rather than hidden behind "and then generalise the schema".

1. **`primary: Bool` encodes one person's priorities.** The field, its comment
   (`Empire/EmpireDashboard.swift:357-358`), the sort at `:363` and the mint dot at `:396` all
   exist to float five specific brands. There is no mechanical translation. Either it becomes
   a user-controlled `pinned` flag with an empty default, or it is deleted. That is a product
   decision, and it is Track B's.
2. **`sourceBadges` hardcodes six vendors** at `Empire/EmpireDashboard.swift:336`:
   `["stripe", "asc", "github", "render", "cloudflare", "support"]`. A stranger's registry
   might report none of them. The row must become data-driven from the snapshot's own
   `sources` dictionary, which changes the layout, because six fixed slots and an unbounded
   set are different designs.
3. **The server is not in this repository.** `the excluded operator snapshot service` is a Python
   service that aggregates Stripe, App Store Connect, GitHub, Render and Cloudflare. The
   client migration produces a documented JSON contract that a stranger can implement, and
   nothing more. The inline `grux.portfolio.projects` list exists precisely so the feature is
   usable with no server at all, and that path deserves to be the primary one in the OSS
   build.
4. **`~/.grux/empire-snapshot.md`** (`Empire/EmpireDashboard.swift:100-105` and `:160-186`) is
   a markdown mirror written for the owner's CLI smoke tests. It is not a feature, it is a
   personal workflow. It should be dropped, not ported, and the decision should be recorded
   rather than made silently by whoever does the port.
5. **Telemetry is a separate migration with a wider blast radius.** Contract section 4 settles
   the policy; the code change touches every `PostHogTelemetry.shared.track` call site, and
   the hardcoded `distinctId` at `Telemetry/PostHogTelemetry.swift:32` must be removed
   regardless of whether analytics is on, because it identifies a real person.
6. **`URLGuard` will block the migrated feature for many legitimate users.** A user who
   points `grux.portfolio.registry_url` at their own LAN service gets denied:
   `Security/URLGuard.swift:178` rejects `192.168.0.0/16`, `:176` rejects `10.0.0.0/8`, `:175`
   rejects loopback, and the built-in allowlist at `Security/URLGuard.swift:43-46` contains
   the owner's two hosts and nothing else. There is a user-editable allowlist
   (`Security/URLGuard.swift:53`, sourced from `SecurityPolicyStore`), but it has no key in
   contract 2.5, so a user cannot satisfy `endpoint.registry` for a LAN host through
   configuration. This is raised as CR-3 in section 9.

## 8. Adoption order

Not a schedule, a dependency order. Each step is independently shippable and leaves the tree
working.

1. Contract mirror plus `check-contract` with **only** the I3 dead-private-function check.
   No codegen, no refactor. It finds `judgeText` on day one and costs almost nothing.
2. `GruxContractGen` emitting `Capability`, `ConfigKey` and `FeatureID`. Nothing consumes
   them yet.
3. `CapabilityResolver` plus `FeatureGate`. Migrate one feature, the portfolio dashboard,

4. The capture privacy layer, section 6. It is independent of steps 2 and 3 and is the

5. `effective` and `display` accessors, key by key, with K1 and K2 enforced only on migrated

7. The remaining 11 features through the recipe in 7.1.

## 9. Contract change requests

Each is a proposed exact entry plus the reason. None of them is used anywhere else in this
document as though it had been accepted.

### CR-1. A closed feature id set

**Proposed addition: contract section 7, "Feature registry".** A table of stable feature ids
with the same rules as section 1: closed set, stable ids, never renamed.

**Why.** The contract closes the capability vocabulary and the config namespace, and it
defines four feature **states**, but it never defines what a feature **is**. Section 1 of this
document needs `FeatureID` to be a generated closed enum for the same reason `Capability` is:
so a feature cannot be invented at a call site. Track B needs the same ids to say which
feature a blueprint targets. Two tracks minting ids independently guarantees they diverge, and
the reconciler cannot catch a divergence in a vocabulary the contract does not own.

**Proposed initial entry, as a shape rather than a full list:**

| id | label | sidebar group |
|---|---|---|
| `portfolio` | Portfolio | command |

The full set should be derived from `SidebarIA.groups`
(`Sources/Grux/DesignSystem/SidebarModel.swift:27-74`), which already enumerates 36 tabs, and
then pruned to what the OSS build ships.

### CR-2. `needs-setup` for a reason that is not a missing capability

**Proposed change: contract section 3**, to admit a non-capability setup step carrying its own
`label` and `remediation`, in the same shape as a capability row.

**Why.** Contract section 5.4 states that while `grux.capture.first_frame_reviewed` is
`false`, the focus loop is `needs-setup`. Contract section 3 defines the `needs-setup`
rendering entirely in terms of missing capabilities: "a setup card overlaid listing each
missing capability by `label` and its `remediation`". An unreviewed first frame is not a
capability, has no `label`, and has no `remediation`, so section 3 as written cannot render
the state section 5.4 requires. The two sections do not currently compose.

**Proposed entry, whichever form is preferred:**

Either add to section 1.2 or a new class:

| id | label | remediation |
|---|---|---|
| `setup.first_frame_review` | First frame review | Grux will take one screenshot and show you exactly what it would send. Nothing leaves your Mac until you approve it. |

Or amend section 3 to read "listing each missing capability or setup step by `label` and its
`remediation`" and give section 5.4's flag those two strings inline.

The first form is preferable, because it keeps one rendering path and one data shape.

### CR-3. A config key for user-trusted hosts

**Proposed addition to contract 2.5:**

| key | owner | type | secret | default | notes |
|---|---|---|---|---|---|
| `grux.security.url_allowlist` | security | list | no | `[]` | hosts the user permits despite the private-address guard |

**Why.** Five of the nine `endpoint.*` capabilities in contract 1.3 are things a user
typically runs on their own machine or LAN: `endpoint.ollama`, `endpoint.registry`,
`endpoint.media_service`, `endpoint.webhook_inbox`, and `endpoint.uptime_targets` when
pointed at an internal service. `URLGuard` denies loopback (`Security/URLGuard.swift:175`),
`10.0.0.0/8` (`:176`), `172.16.0.0/12` (`:177`) and `192.168.0.0/16` (`:178`) by default. So a
user who follows the remediation text for `endpoint.registry` and enters their LAN URL gets a
denial with no key in the namespace to fix it.

A user-editable allowlist already exists in the code (`Security/URLGuard.swift:53`, fed from
`SecurityPolicyStore.shared.policy.urlAllowlist`), so this request adds a config key for
something already implemented rather than a new mechanism. Without it, the capability's
remediation string promises something the guard refuses, which is the same class of defect as
a lying toggle: a claim to the user that the code does not honour.

The default must stay `[]`, for the same reason contract 1.3 gives for endpoints. The two
entries currently hardcoded at `Security/URLGuard.swift:43-46` are the owner's hosts and must
be removed from the OSS build regardless of whether this request is accepted.

## 10. Findings that contradict or refine the stated facts

Reported as instructed. Nothing here changes the specification above; two items sharpen it.

**Confirmed exactly as stated.**

  properties run from `:564` (`anthropicApiKey`) to `:629` (`offlineMode`), with `CodingKeys`

  `Sources/Grux/KeychainStore.swift`.
- The focus loop transmits a JPEG at `FocusWatcher.swift:213` via `ScreenCapturer.jpegData`.
- Redaction runs at `FocusWatcher.swift:498`, `return SecretRedactor.redact(body)`.
- OCR fencing is at `FocusWatcher.swift:530`, `SecretRedactor.wrapAsUntrusted("screen_ocr",
  ...)`.
- `judgeText` has exactly one mention in the tree, its own declaration at
  `FocusWatcher.swift:524`.
- `focusUseVision` has exactly six mentions, five of them declarations or coding keys in
  `Models.swift` and one banner label at `LaunchRootView.swift:863`.
- The capture-interval slider reports a cadence the loop does not use.
  `FocusWatcher.swift:110` reads `tier.cadenceSeconds`.
- `grep -rniE 'excludeApp|excludedBundle|blocklistApp|excludedApps'` over `Sources/` and

**Refinement 1: the environment-variable count is 24 only for `Sources/Grux`.** The stated
figure of 24 is correct for `grep -rn 'ProcessInfo.processInfo.environment' Sources/Grux/`.
Across the whole `Sources/` tree, including `GruxShellCore` and `GruxAgentCore`, it is 39. The
extra 15 are mostly subprocess environment construction for agent CLIs rather than config
reads, so 24 is the right number for the precedence rule in contract 2.3. Worth pinning so a
later audit does not think the count drifted.

**Refinement 2: the `KeychainStore.swift:14` citation points at a comment.** Line 14 is
`// - kSecClassGenericPassword, service com.dcj.grux, account = key name.` The code is at
`KeychainStore.swift:80`, `:125`, `:148` and `:164`. The fact is correct; only the line is
imprecise, and the comment is an accurate description of the code, so this is a citation
correction and not a behaviour correction.

**New finding, and it matters: the OCR fence never executes.** Contract section 5.1 cites
`FocusWatcher.swift:530` as evidence that "the OCR is fenced". That line is inside
`judgeText`, which section 5.1 of this document proves is unreachable: one occurrence in the
file, and `private`. So the fence exists in source and never runs. This does not create a
leak, because the dead path is the only OCR-to-model path in the focus loop and it is dead;
prescreen OCR at `FocusWatcher.swift:186` populates `state.lastOcrSnippet`
(`FocusWatcher.swift:189`) for display and is not sent to the model. But the contract's
statement is true of the code as written and false of the code as executed, and a future
change that revives the OCR path would inherit a guarantee nobody has tested. Recommendation:
either delete `judgeText` and correct contract 5.1, or wire it and add a test.

**New finding: `SCContentFilter` already accepts the exclusion list and is passed an empty
one.** `ScreenCapture.swift:124` reads
`SCContentFilter(display: display, excludingWindows: [])`. The mechanism section 6.3 needs is
one argument, at a line that already exists. This is a smaller change than the "no privacy
layer exists" framing suggests, and it is worth knowing before anyone designs a
post-capture filter.

**New finding: window-title exclusion fails open if built on the existing title source.**
`ActiveApp.frontWindowTitle` (`ActiveApp.swift:20-31`) requires Accessibility and returns
`""` on failure via `ActiveApp.swift:16`. Any title blocklist built on it silently matches
nothing when `perm.accessibility` is absent. `SCWindow.title` is the correct source and
requires only Screen Recording. Section 6.3 specifies the latter.

**New finding: the cost ceiling is enforced as a call count, and silently.**
`FocusWatcher.swift:196` compares `cloudCallsToday >= tier.maxCloudCallsPerDay` and, on
tripping, writes to `NSLog` at `:197` and sets `shouldCallCloud = false`. Contract section 3
requires a dollar ceiling that produces a visible `degraded` transition. The gap is both the
unit and the visibility.

**New finding: the analytics default is confirmed opt-out.**
`Telemetry/PostHogTelemetry.swift:45` and `:92` read `GRUX_POSTHOG_DISABLED == "1"`, a kill
switch, so telemetry is on unless disabled. A project token is hardcoded at `:30`, a host at
`:31`, and `:32` hardcodes a `distinctId` that is the owner's personal email address. This
confirms contract section 4's claim about the private tree, and the `distinctId` is a
personal-data leak that must be removed independently of the analytics decision.
